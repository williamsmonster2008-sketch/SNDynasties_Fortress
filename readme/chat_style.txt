# 南北朝坞堡模拟器 - 最终调试进度记录

## 📋 项目概述

**项目名称：** 南北朝坞堡模拟器架构重构  
**当前阶段：** 数据传递问题修复（最终阶段）  
**完成度：** 99% （游戏成功启动，正在解决角色数据显示问题）

## 🎯 项目背景

**游戏设定：** 中国南北朝时期模拟经营建设游戏，一群流民（4-5户、20口人左右）在山西境内某僻远山谷建设坞堡，从零开始发展成200多人聚落的过程。


**核心特色：**
- 五代同堂家族关系网络（高祖到玄孙）
- 具有深度的人格系统以及人际交互模式设计
- 南北朝时代特色姓名系统（门阀士族、胡族复合姓）
- 智能事件通知和实时状态更新
- 现代化组件化界面设计

## ⚡ 对话风格要求

### 🎯 核心原则
1. **言简意赅** - 每一步操作询问用户后再执行，不要自行展开过多对话内容
2. **避免长篇大论** - 防止对话过长被迫重开，保持对话简洁高效
3. **直接给出操作步骤** - 告诉用户具体在哪个文件的哪一行如何修改，而不是自动生成修复代码
4. **一次解决一个问题** - 专注当前错误，不要同时讨论多个话题或扩展其他功能
5. **优先project_knowledge_search** - 总是先搜索项目知识库，除非用户明确要求web搜索
6. **全局架构思维** - 在分析问题时必须从整体架构出发，考虑模块间的数据流和依赖关系
7. **具体可操作** - 提到需要修改某个模块或改进某种方法时，必须给出具体的修改内容以及修改位置，给不出来就不要说
8. **避免硬编码** - 在添加模块代码时，尽最大可能避免硬编码，将可调配数据集成到静态数据表中
9. **要我做的事情如果依赖于上一步的执行结果，那就先只告诉我第一步，等有了执行结果再告诉我第二步，不要一下都说出来引起误解

### 📝 回复格式
```
**问题：** [简短描述当前问题]
**修复步骤：**
1. 打开 xxx 文件
2. 找到第 xxx 行
3. 将 [具体代码] 改为 [具体代码]
4. 必须说明是修改模块代码还是控制台调试代码，如果是前者请说明模块文件名以及修改位置
**完成后：** 告诉我结果
```

### ❌ 避免的回复方式
- 长篇的技术解释
- 自动生成大量代码
- 同时提到多个问题
- 过多的背景介绍
- 不必要的祝贺或鼓励
- 不使用project_knowledge_search就直接回答
- 局部思维，不考虑整体架构的影响
- 过于简略不具备可操作性的内容
- 避免硬编码，优先使用静态数据表

### 🧠 架构思维要求
**在解决任何问题时，必须考虑：**
- 数据从哪里来（GameEngine → GameStateManager → GameInterface）
- 数据如何传递（事件总线 vs 直接调用 vs 状态订阅）
- 组件间的依赖关系（父子组件、状态共享、方法调用链）
- 时序问题（构造函数执行顺序、DOM创建时机、数据更新时机）
- 全局影响（一个修改可能影响多个模块的表现）

###执行思路中绝对要避免的问题
1. 控制台指令达到目标了就判定为任务完成，半场开香槟。
2. 之前制定了相对合理的架构和执行步骤，在一步步执行过程中居然会遗漏掉已经定好的步骤，譬如架构中写了要新建四个模块，结果完成三个模块后就迫不及待的要求进行测试。这是绝对绝对不允许出现的情况！
3. 优先级最高的决策是在既有完整架构下查找并解决问题，而不是为了尽快跑通流程在调试过程中不断给出简化建议，甚至直接搁置某个有问题的模块，用写死代码的方式来试图解决问题。

**调试和修复任务的步骤化指导原则**

当指导用户进行调试或修复任务时，如果后续步骤依赖于前一步的执行结果：

1. **只提供第一步操作** - 给出具体的代码或操作指令
2. **等待执行结果** - 让用户运行并提供输出/反馈
3. **基于结果给出下一步** - 根据实际执行结果制定针对性的后续步骤
4. **避免预设性指导** - 不要一次性给出多个步骤，避免基于假设的指导造成误解

这样确保每一步都基于实际情况，提高调试效率和准确性。
